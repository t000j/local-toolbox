# 工具箱功能完整性与日常可用性审计

日期：2026-10-01  
审计基线：`feat/data-format-tools-batch-01`，提交 `893117106486a0c1e5a1d227cf19a17b58683743`

## 结论先看

97 个注册工具都有实际实现，整体已经是能完成不少小任务的工具箱，不是97个空壳。但“99项原始工作流已实现”不能替代“97款工具达到日常可靠可用”：旧 JSON、计算器、单位换算、批量改名、截图标注等还有基础结果正确性或操作闭环缺陷；PDF、ZIP、大文件、中文旧编码等则需要把实际适用范围说清并按目标用户补齐。

建议先暂停堆新工具，把工作分成三层：

1. **先修正确性与损失风险**：不静默改数、不确认旧计划执行新计划、不误拒普通PDF正文、不把多帧/多页输入悄悄当单图、不丢未保存编辑
2. **再补日常闭环**：计时跨页持续、批量结果一次保存、排序保留缩略图、裁切原图定位、导出真实落盘、失败能知道哪些已完成/待恢复
3. **最后按用途扩范围**：中文文本GBK/GB18030、较大下载文件、一般ZIP资料包、带链接/书签的正常PDF。不要为了“全完成”取消安全检查或承诺全部格式

本报告没有发现可据此断言“所有受支持输入都会失败”的问题，也没有给未实际测试的模块打运行通过标记。下面的“基本可用”仅指源码中的最小实用流程成立。

## 文本与数据、哈希及文本编码工具：只读静态完整性审计

### 结论

这批模块不是一排只摆了界面的占位功能。22 项都有实际处理逻辑，大部分已实现小型本地工具所需的输入、处理、反馈、结果利用闭环。明显较弱的是旧的 JSON 格式化与 JSON Diff：存在静默改数、旧结果冒充当前结果、无资源边界等基础问题。JSONPath 的工程闭环较完整，但沿用原生 JSON 数值解析，安全数值校验仍有缺口。

应优先修好结果可信度和导出闭环，再讨论扩展范围。不要把 SQL 不执行数据库、JWT 不验签、Markdown 不加载图片、校验和不替用户判断来源等明确设计边界算成“半成品”。也不能把“有按钮”和“下载函数调用了 click”当成 Windows 桌面实机验收通过。

#### D1 · P1 · JSON 格式化和 Diff 会静默损坏数字/掩盖差异

**证据等级：确定算法错误**（数字精度/溢出/下溢）；重复键是确定的成员丢失行为，属于需明确的输入范围口径。

**手工复现**：

1. 格式化输入 `{"id":9007199254740993}`，解析后的 Number 为 9007199254740992，输出改变业务 ID，却显示“JSON 校验通过”
2. Diff 左侧 `{"id":9007199254740992}`，右侧 `{"id":9007199254740993}`，两边变成同一个 Number，结果显示一致

**最小改进**：采用保留数字词法的解析/格式化路径；如果暂不支持，至少在处理前明确拒绝会丢失信息的数字和重复键，不能在已损坏的 Number 上才试图还原。Diff 的显示值也必须对应比较值。

**验收**：上述四组输入必须原样保留对应数值/成员，或明确报“无法无损处理”；不允许变值后成功，不允许不同 ID 被报一致。普通对象键重排仍应报一致。

**证据等级：条件竞态或故障风险**。无界主线程递归/渲染路径确定存在，但触发栈溢出或卡顿的深度、规模、耗时依赖 WebView；不声称已发生实机崩溃。Diff 的 resetResult 只清旧结果，不限制输入或保护递归异常。

#### D4 · P2 · JSONPath 数值保护仍漏掉下溢和非整数精度损失

**证据等级：确定算法错误**。已复核现有有限值/安全整数 guard；下溢后的 0 和普通舍入后小数确实不会被其拒绝。

**证据等级：产品范围 / 基础结果利用缺口**。目前屏幕比较功能确已实现；此项不是声称比较按钮无效，而是指出没有一次性带走完整差异的路径。

- **实际闭环**：文本或本地文件编码；Base64文本解码为UTF-8文字或二进制 → Worker转换/规范填充位检查 → 预览、完整复制/保存。`base64.ts:6–38`；`Base64Tool.vue:19–68,78–111`

- **实际闭环**：方向/是否编码非ASCII → 常见命名实体、数字Unicode标量单层转换 → 纯文本显示、复制、交换。`htmlEntities.ts:1–24`；`HtmlEntitiesTool.vue:10–28,40–64`

- **实际闭环**：查看/UTF-16或码点编码/转义解码 → 按码点与孤立代理项形成分页表 → 码点、UTF-16偏移、码元、转义、结果复制。`unicode.ts:20–81`；`UnicodeTool.vue:14–31,43–91`

- **需要补齐/验收**：未发现必须添验签功能。验收三段正常令牌、空签名段、非法Base64URL位、JWE和非对象载荷拒绝；含大整数/重复键的payload显示与原始JSON一致。复制明确警告可进入系统剪贴板历史可作为文案一致性小改进

- **最小改进/验收**：无效新请求清除或标为上批次结果。生成10→数量0→再生成不应把10条当新结果；v4第三段首字符4、variant为8/9/a/b；1、100边界；随机源不可用明确失败

#### 20. `hash` · 哈希摘要

- **实际闭环**：UTF-8文本（含空串）或本地文件 + MD5/SHA-1/256/384/512 → Worker里1MiB分块WASM摘要 → hex显示/复制，30秒取消和过期结果清除。`hash.ts:3–19`；`HashTool.vue:10–35,42–69`
- **判断**：小文件及文本摘要基本完整，确实分块读文件；不是把文件一次载入内存后假称分块
- **明确边界**：文本最多1MiB个UTF-16码元（并非UTF-8字节），文件256MiB/30秒；MD5/SHA1安全用途警告已实现。几百MiB安装包/ISO是当前不支持的常见场景，而非算法错误
- **需要补齐/验收**：用已知空串/abc摘要与外部可信实现核对每个算法；跨1MiB边界、空文件、取消→换文件不能旧值回写。若目标是通用下载文件校验，优先评估基于既有流式读取支持更大文件和进度/合理超时；这是范围扩展，不冒充现有256MiB范围内缺陷。文本孤立代理项会由TextEncoder替换，宜与Base64统一为严格拒绝/明确口径（`hash.ts:11–12`）

#### 21. `checksum-verify` · 文件校验和验证

- **实际闭环**：选算法/纯hex、GNU或BSD单记录 + 可信预期值 + 文件 → 解析格式/算法长度/文件名核对 → 分块计算实际摘要 → 一致/不一致与双方值。`checksum.ts:11–46`；`ChecksumTool.vue:11–24,29–53`
- **判断**：校验小型下载文件的基础闭环完整；实际比较内容哈希，不只比较文件名/大小
- **明确边界**：256MiB/30秒；仅单条、无目录的文件名；GNU转义文件名/多条清单不支持；不自动访问清单路径；区分摘要一致与来源可信。文件名不相同可显式改纯hex，提示中已有安全出口
- **需要补齐/验收**：相同内容/改1字节/空文件；大写hex；GNU两空格和星号；BSD算法不匹配、文件名不同、多行记录拒绝；取消和改任一输入清旧结论。与hash同列“大型下载文件”实用范围扩展，不能宣称支持ISO

#### 22. `text-encoding` · 文本文件编码转换

- **实际闭环**：本地文件 + 明确源/目标编码 + BOM策略 → Worker严格解码/表示能力检查/编码/往返校验 → 文字预览与字节统计 → 选新位置另存；Rust排他新建、拒绝覆盖/重解析路径，写入后同步。`textEncoding.ts:15–89`；`TextEncodingTool.vue:14–36,40–72`；`binaryExport.ts:4–12`；`src-tauri/src/binary_export.rs:12–27`；`safe_file_io.rs:23–34,36–58,65–80,95–109`
- **判断**：在明示的5种编码范围内闭环最完整之一，“严格转换”有实质保障，不是仅TextDecoder→下载的包装
- **明确边界**：UTF-8、UTF-16LE/BE、ASCII、ISO-8859-1；不自动猜测，不支持GBK/GB18030/Shift-JIS/UTF-32；4MiB源/16MiB输出/10秒；仅Windows桌面保存；仅本地驱动子目录新文件，不支持根目录/网络路径/覆盖。保留换行/NUL/组合形式
- **需要补齐/验收**：中文Windows用户常见“GBK→UTF-8”无法完成，应明确作为下一批最有价值的基础场景扩展；不能把此受限版称为通用中文旧文本修复器。当前验收覆盖中文+emoji+CRLF、BOM冲突、保留BOM避免双加、错误UTF-8/奇数UTF-16拒绝、中文→ASCII拒绝、已有目标拒绝、另存取消、保存失败清理、重新读落地字节对应所选编码。实际Windows保存未在本次运行

### 建议的收尾顺序

1. 先解决 D1–D4：数值不静默改变，结果不与输入错配，输入边界不会拖死应用。这是“可信基础工具”的最低线
2. 补 JSON Diff 一次性复制结果、Unicode合法结果往返，修正正则截断文案/判断；不必同时开发高级功能
3. 在 Windows 打包版验证 CSV / Synthetic / Base64 下载和编码另存，记录输出路径、取消/失败与字节回读证据。静态源码只能证明有实现，不能替代用户最终拿到文件
4. 再按目标人群决定范围：中文Windows文本优先GBK/GB18030，下载完整性工具优先大于256MiB文件；保持“不支持”的诚实提示。不要用新增工具数掩盖现有工具的结果可靠性

### 最终判断边界

本次足以确认实现路径、指出确定性逻辑问题及应覆盖的验收，不足以声称全部22项已在Windows安装版工作正常，也不主张其余未发现缺陷的模块绝对没有bug。可以合理说：大多数是有用、范围受限的基础工具；JSON两项最需要完成基础收尾，另有几个小而具体的跨工具一致性与边界缺口。

### 一、结论

- 这批工具不是只有标题和按钮的占位页。文件扫描、清单、结构比较、分割合并、ZIP、图像处理和 PDF 页面复制都存在实际处理与结果出口。
- 文件类多数可以完成一个小而清楚的任务；没有自动删除重复文件、没有同步文件夹、拆分不一次生成所有分卷，都不能单独作为“半成品”的证据。
- PDF 的主要问题是实际可接纳范围。8 个读取已有 PDF 的工具共享非常严格的静态文档门槛；带链接、注释、书签、标签、增量保存等文档会直接拒绝，元数据查看也不例外。在这个范围内可完成处理，但不宜表述为“日常 PDF 已普遍可用”。
- 存在不应被“限制已经写在说明里”掩盖的具体问题：普通文本触发 PDF 伪语法拒绝；改名预览可能与实际执行规则不一致；改名失败恢复缺少逐项回执；PDF 排序一移动就清掉内容缩略图。
- 本轮没有证实新文件导出会覆盖已有文件。PDF／ZIP／清单／文件分块的新建输出使用独占创建。批量改名是另一路实现，存在竞争条件及部分回滚问题，应优先核查；图像静态化损失另见图像审查。
- 图像专项已完成：11项也都有真实闭环。原生格式转换／压缩接受APNG及多页TIFF但只输出单幅，操作页仅披露GIF/WebP静态化；PNG“无损优化”不保留ICC颜色解释，原图缩略图也走相同转换路径。这是衍生文件内容／颜色语义的缺口，原文件仍保留。详情、锁定依赖源码和11项inventory见 `image-audit.md` 的IMG-01/02。

### 三、先修的文件正确性问题

#### F1 · P1：批量改名的“已预览规则”没有绑定到执行

**证据**：`components/BatchRenameTool.vue:30–34` 规则变更仅清空预览；`70–77` 异步预览直接赋值，无 revision／快照校验；`146–156` 规则控件没有 `disabled=loading`；`85` 执行重新读取当前 `rule.value`。后端 `file_rename.rs:226–236` 又用这份当前规则重建计划。

**可复核推演**：选 `report.txt`，前缀设 `old-`，点预览；在原生预览响应回来前改为 `new-`。watch 先清空旧结果，随后迟到响应重新填入 `old-report.txt`。确认时提交的却是 `new-`，最后得到 `new-report.txt`。这不是用户没有点确认，而是确认内容与执行内容不一致。

**改进／验收**：预览计划绑定不可变源清单、规则、文件身份和版本；任一变化废弃迟到结果。执行精确提交已确认的计划，后端复查身份与目标。用延迟响应场景验证：过期预览不得重新出现、不得启用确认；最终路径必须等于可见确认清单。

#### F2 · P1：改名失败后缺逐项恢复闭环；路径级竞争还可能触及已有内容

**证据**：`src-tauri/src/file_rename.rs:192–200` 一次检查全部源路径／目标不存在；`205–215` 随后按路径 `fs::rename`，错误时逆序回滚但丢弃每次回滚错误，只返回“已尝试”。`RenameRecord` 仅 oldPath/newPath（35–40），无文件身份；UI 只有成功返回才更新 undoRecords（`BatchRenameTool.vue:85–97`）。

**推演一，恢复缺口**：A改名成功，B因被占用失败；若A的新路径也被占用导致回滚失败，则最终目录里A已改名、B未改名，UI没有“哪些仍需恢复”的回执或本批次恢复列表。其提示没有假称回滚全成功，但工具无法把这项工作做完。

**推演二，覆盖风险，尚未实机验证**：检查“目标不存在”与真正 rename 之间有时间窗；另一进程在期间创建同名目标，普通替换型 rename 不是独占 no-replace 操作。逆向回滚同样没有原路径冲突保护。应在 Windows 用可控竞争夹具确认目标文件内容是否会被替换，不能仅凭早先 `exists()` 宣称绝不覆盖。

**改进／验收**：选择不覆盖语义的原生 rename，持有／核对源身份；回滚也不覆盖外来对象；返回每项“未开始／已完成／已恢复／恢复失败”及精确路径。注入第二项失败和回滚失败，不能吞状态；创建目标竞争时已有目标内容必须保持不变。撤销记录应全局可取，或明确仅当前页／当前会话；当前UI在成功消息被清除且无预览时甚至没有显示撤销按钮（`BatchRenameTool.vue:36–45,166–175`）。

#### F3 · P2：仅大小写的改名被误判为“不变”

**证据**：`file_rename.rs:42–44` 路径整体 lower-case；`136–137` 同折叠路径直接设 unchanged。

**推演**：`REPORT.txt` 查找 `REPORT` 替换 `report`，规则有效，目标文本不同，但结果为不变，无法完成一次普通的大小写规范化。

**验收**：Windows通常不区分大小写目录中仍可显示并执行安全的大小写改名；真正字符完全一致才是 unchanged。若暂不支持，直接显示“仅大小写改名暂不支持”，不要显示已经不需改。

#### F4 · P2：磁盘顶层占用的显示标签参与主键，导致两组相加

**证据**：`src-tauri/src/disk_tools.rs:42` 用实际顶层目录名或固定文字“根目录文件”作相同类型的 key；`51–52` 按该 key 累加。

**推演**：所选目录下存在 `a.bin`（200字节），同时有真实子目录 `根目录文件/b.bin`（100字节）。两者被合计成同一“根目录文件”组300字节，无法看出子目录实际只占100字节。总量正确，分组不正确。

**验收**：根文件桶使用独立枚举／稳定ID，显示文案与目录身份分离；上述树显示根文件200、同名字目录100两个可区分项目。

#### F5 · P2：扫描结果预算令中等目录“只看到一截”，没有继续／缩小范围的闭环

**证据**：前端声称最多1,000结果，但后端 `native_scripts/file_scan.ps1:74–80` 先以55KiB序列化行预算停止；遍历10,000项、1,000目录、深32（84–91），搜索内部22秒／去重枚举11秒、总哈希22秒（108–116,125–153）。UI有25行分页，但那只是已经收到的结果分页（`FileScanPanel.vue:14–15`），不是继续扫描。

**实际意义**：几百条带长中文路径的文件就可能碰输出预算；去重即使继续存在匹配文件也不能扩展候选；清单与两树比较沿用同一预算。当前“结果不完整／未知”提示是正确处理，不应说它把缺项误报不存在。

**改进／验收**：优先提供相对路径紧凑传输、可继续分页／流式导出或用户可见的范围拆分入口。建立≥2,000项、含长中文路径的夹具，能得到完整清单或明确可继续，不把本地显示分页误称完整扫描。不需要新增文件删除权限。

#### F6 · P2：ZIP 有完整小包工作流，尚不能胜任一般资料打包

**证据**：`zipArchive.ts:4–7,38–45,52,67–68,175–179` 限制容量、条数、编码；`ZipArchiveTool.vue:122–125` 明示范围和不保留元数据。

**验收**：先决定产品定位。如果仍称一般ZIP管理，至少在真实常见资料包中验证较大文件、多文件、UTF-8中文/空目录往返；扩容应走流式读取／写入与有界解压。旧编码需显式选择且保留路径安全校验，不应猜编码。时间戳恢复可作为普通备份需求的可选项，不能把当前已明示不保留称为隐蔽数据损坏。

### 四、PDF 的日常可用性与具体问题

#### P1 · P1产品缺口：八个工具复用“可安全重写静态页”准入，简单只读也被连带拒绝

入口关系已在源码确认：
- 元数据：`pdfMetadata.ts:12` → `loadPageDocument`
- 文本：`pdfTextExtract.ts:13` → `loadPageDocument`
- 转图片：`pdfRasterPrepare.ts:7–9` → `loadPageDocument` ＋预览资源审核
- 压缩：`pdfImageCompression.ts:39` → `loadPageDocument`
- 拆分／排序／旋转：`pdfPages.ts:11–17,29` → `admitPdf` ＋ `auditPdf`
- 合并：`pdfMerge.ts:29–36` →相同准入／审查

`pdfAudit.ts:4,24–31` 拒绝书签 Outlines、标记／标签结构、OutputIntents、动作以及非空 Annots（注释／链接）。`pdfClassicXref.ts:24–28` trailer仅允许Size/Root/Info/ID；`pdfRawSyntax.ts:8,66` 明确拒绝Prev等。`pdfAdmission.ts:11–15` 限输入8MiB及规范PDF1.0–1.7。页数上限200（`pdfAudit.ts:55–62`）。

**推演案例**：给一个原本可处理的单页静态PDF加一个普通URI链接注释；或者只加正确书签／标签结构；或者用标准增量保存添加标题。即使用户只是想读页数、提取已有正文、把第一页另存图片，也在公共入口失败。这里不是要求执行链接或绕过密码。

**合理完成标准**：
1. 保留结构安全、资源预算和不执行动作的底线，同时按“只读属性／只读文字／渲染／页面结构改写”拆分能力门槛
2. 对带链接、标签、书签、正常增量版本的可信样本文档，至少让只读属性与文字工作流可用；页面改写若不能保留功能，提前精确说明并拒绝，不能偷偷丢弃
3. 用真实来源类型的非隐私样本建立支持矩阵，例如文字办公文档、带链接报告、单页扫描件、多页扫描件、带书签手册；报告成功率与拒绝原因。不要仅用自己生成的简化PDF证明“普通PDF已完成”

此处是产品兼容性欠账，不是建议删除检查或容忍静默损坏。允许明确宣传为“小型静态PDF工具”，但这与通用完成度是两件事。

#### P2 · P1：把正文／元数据中的普通字节当PDF语法，产生可确定的假阳性

**a. 普通大写英文 BILL 使预览、转图、文本提取失败**

`pdfPreviewGate.ts:87–91` 对所有非证明为字体／图片的解码流，只要出现连续字节`B`、`I`就失败，并未检查它是操作符、字符串还是注释。该函数也由文字专用路径使用（同文件12–16、`pdfTextResources.ts:8–9`）。

**最小推演输入**：规范PDF1.4、经典xref、单页、Type1 Helvetica、直接Length，内容流为 `BT /F1 12 Tf 10 10 Td (BILL) Tj ET`。其中没有BI内联图操作符；文字字符串包含BI就被拒绝。普通字符串`BINARY`、`BIRD`同理。页面复制／旋转不调用预览审核，因此同一文档可能能旋转却不能提取文字／转图。

**b. 标题里写 /Prev 会使所有公共PDF读取入口失败**

`pdfRawSyntax.ts:9–20` 明确连字符串、注释、流载荷一起扫描结构名字；`pdfClassicRecords.ts:7` 在真正读结构前调用。

**最小推演输入**：规范单页PDF的Info含 `/Title (Notes about /Prev entries)`，没有增量xref。`/Prev`后面的空格满足分隔条件，仍会被报告“不支持Prev”。图像／字体的二进制载荷碰到同样字节也有可能，但无需依赖随机碰撞才能证明这个问题。

**改进／验收**：在预算内按PDF词法／对象／流边界识别真实结构；保留真正的BI、Prev、ObjStm边界检查。成对夹具必须覆盖“相同文本在字符串／注释中通过、真实结构位置按规则处理”。错误信息应区分真正不支持与保守语法检查，不能把正常正文称作图像／增量功能。

#### P3 · P2：PDF排序的视觉反馈在每次移动后消失

**证据**：`components/PdfPageThumbnails.vue:13–15` 监听`props.order`即clear；clear撤销全部预览URL；`32–39` 必须再点击“生成这组缩略图”。

**推演**：生成第1–12页缩略图，凭图识别第4页并上移一次；所有图立即变成“尚未生成内容预览”。还想凭图将其他页移到位置时要重新生成。每移一步可能重新审核／渲染整组，基本“看图整理页序”被打断。

**验收**：缩略图按源文件身份＋原页号缓存，重排只改变展示顺序，不抹除未变化的页面图；新文件或影响渲染的变化才失效。连续三次换序无需再次生成且图与原页号始终一致，跨12页边界也不丢失身份。缩略图失败不应禁用本来可以安全执行的页面复制。

#### P4 · P2：PDF转图缺合理DPI反馈和多页一次保存

**证据**：`pdfRasterLimits.ts:3,16–18` 每页4,000,000像素；`PdfImagesTool.vue:43` 提供36–300DPI；`28–34,47` 只有逐页调用保存对话框。

#### IMG-02｜P2：PNG“无损优化”不保留 ICC/颜色解释，且原图预览不能暴露这种差异

**涉及：** `image-compression`，同一实现也影响 `image-format`

**源码事实：**

- 只提取方向，随后构建 `DynamicImage`，没有提取 ICC、按源配置转为 sRGB 或回填配置：`src-tauri/src/image_codec.rs:39-42`
- PNG 压缩新建 `PngEncoder` 后直接写像素，没有设置 ICC：`src-tauri/src/image_codec.rs:53-60`
- “原图”预览也经过同一解码器和新 PNG 缩略图编码：`src-tauri/src/image_conversion.rs:26-31`、`src-tauri/src/image_codec.rs:62-66`。因此左右看起来相同并不证明和色彩管理正确的源图相同
- 操作页标题和选项是“PNG 无损优化”，只有“EXIF 等元数据不复制”的通用文案：`ImageCompressionTool.vue:97,123,141`
- 锁定依赖源码的 `decoder_to_image` 在读出像素后设为 sRGB；普通输出不传 ICC/CICP。PNG 编码器新建时 ICC 为空，只有显式设置才会写入。[DynamicImage 依赖源码，原始行 1346–1386、1557–1624](https://docs.rs/image/0.25.10/src/image/images/dynimage.rs.html#1557-1624)、[PNG 编码器源码，原始行 632–643、697–703、781–783](https://docs.rs/image/0.25.10/src/image/codecs/png.rs.html#632-643)

**推演复现：** 选择带非 sRGB ICC 的静态 RGB PNG，例如 Display-P3 色块，执行 PNG 无损优化。输出像素通道值可能保持，但颜色配置丢失；在支持色彩管理的查看器中，源与输出可能呈现不同颜色。界面的“原图”缩略图已丢弃同类信息，不能作为保真基准。

**影响与边界：** “ICC 没有保留”已由代码确证；具体色差大小未实测。`docs/image-tools.md:25` 不承诺颜色配置保留，说明当前是有明确能力上限的实现；但这仍是“无损优化”对普通带配置图片不够完整的产品语义，不能靠两张同源处理缩略图证明视觉无损。明确的 JPEG 有损编码和白底合成本身不是缺陷。

**最低验收：** 对 PNG 原配置保留，或用颜色管理转换到明确 sRGB，或识别后拒绝/显著标示颜色可能变化；使用非 sRGB ICC PNG、普通 sRGB PNG、16-bit PNG 对照。正确比较源图的色彩管理后显示，而非只比较本工具同一路径产生的两个缩略图。

#### IMG-03｜目标环境验收项：屏幕取色唯一实现依赖 EyeDropper

`useScreenColorPicker.ts:6,13,18` 仅检查构造器与安全上下文并调用 EyeDropper，没有原生备用取色。缺少 API 时按钮禁用，工具会完全不可用；UI 已如实告知：`ScreenColorPickerTool.vue:21-27`。现有 `scripts/check-screen-color.cjs` 和 `docs/screen-color.md:11` 的证据是 mock，不是 Windows WebView2 真实屏幕取色。

**结论：** 不将“无 fallback”本身判为 bug，也不能把此项计为已经实机可用。最低验收是在目标 Windows 安装包上成功启动、点取主屏/副屏颜色并复制，覆盖取消和重启；若目标环境确实缺失 EyeDropper，再补受支持的原生取色路径或将入口明确标为当前不可用。

#### IMG-04｜图片缩放的“批量”只覆盖计算，保存逐张进行

- 1–8 图确实逐张处理，整批成功后返回：`imageProcessing.worker.ts:10-38`
- 结果面板只选择当前图片并保存，且每次默认同名 `image-edited.png`：`ImageOutputPanel.vue:8-17`、`useImageOutput.ts:15-21`
- 推演：选择 8 张图片→全部缩放成功→必须进行 8 次另存，逐次改名；相同目录接受默认名第二次会因既有文件失败
- 结论：基础批量处理有效，批量导出不完整；UI 已写“逐张另存”，无静默覆盖。实用下一步是保留源名的默认输出名、另存全部与逐项成功状态，不必先做目录递归等高级能力
- 最低增强验收：8 图输出能一次选择目标目录后生成 8 个不冲突文件，逐项汇总失败；如仍保持逐张保存，至少默认名含源名并记录已保存项

#### IMG-05｜坐标裁切能工作，但缺少可用于选区的原图预览

`ImageCropTool.vue:30-45` 只有原始尺寸、X/Y/宽/高和结果面板；源图没有预览/选区覆盖层。任意图片中裁掉一个可见对象必须试输坐标、生成结果。此处不是裁切算法未实现：`imageProcessing.worker.ts:26-29` 确实完成先裁切、再旋转、按输出轴翻转。

最低增强可先给方向校正后的原图加像素坐标/矩形覆盖层，数值输入和选区同步；不要求任意角度旋转、透视校正或专业照片编辑器。

#### IMG-06｜图片转 PDF 对常见手机大图的准入偏窄，生成后没有真实页预览

- 每张最多 400 万像素，4096 边长，累计 1600 万像素：`imagePdf.worker.ts:14-15`
- 例如 4032×3024（12,192,768 像素）JPEG，即使文件不到 16 MiB、只选一张，仍直接拒绝；没有按纸张目标自动缩小的入口
- UI 可以重排/移除，但再次选文件会整体替换列表：`ImagePdfTool.vue:15,31-32`
- 结果只显示页数、文件大小和每图页尺寸，没有页面缩略图或生成 PDF 的打开预览：`ImagePdfTool.vue:37`
- 结论：在明确限制内已能做有用的一图一页 PDF；普通手机照片输入需先去尺寸工具缩小，流程没有一体化。容量限制已披露，不是后台丢图
- 最低增强验收：对超限图在生成前清楚列出不合格文件并给降采样路径；若提高范围，应验证常见 12MP/24MP 图而非只放宽常量。生成后至少能看一张完整页面预览核对方向、边距和透明区域

#### IMG-07｜元数据清除保留了容器密度，但不保留 EXIF 分辨率字段

`imageStripJpeg.ts:49-60` 会重建 EXIF，同时只显式保留 JFIF 密度；`imageStripShared.ts:15-29` 的最小 EXIF 仅含 Orientation/ColorSpace。JPEG 若只用 EXIF `XResolution/YResolution/ResolutionUnit` 记录打印尺寸，这些会随元数据一起消失。压缩图像本身不变，但物理尺寸信息可能改变。

这不是已经观察到视觉畸变的证据。它是应补充的显示/打印边界：UI `ImageMetadataStripTool.vue:36` 声称保留像素比例，但没有区分 JFIF/pHYs 与 EXIF。最低验收用仅有 EXIF 300 DPI 的 JPEG 验证，选择保留安全的分辨率字段或明确告知打印密度会被移除；不要声称所有必要显示信息均完整保留。

### 每个工具的最小实用验收样例

以下为后续验收设计，本次未执行。

#### 1. Favicon

- 200×100 静态透明 PNG 生成 32×32 contain 图，应缩成 32×16 并上下透明留白；cover 应居中选取 100×100 再缩放
- ICO 应含 16/32/48/64/128/256 六个正确尺寸图层，独立读取器能够逐层读取；预览为最大图层，保存为 ICO 而非改后缀 PNG

#### 2. 图片调色板

- 2×2 RGBA 样例：两个不透明红、一个不透明蓝、一个完全透明，提取两色，应得到红/蓝且约 66.7%/33.3%
- Alpha 128 的色块在阈值 200 时排除；全部透明应有可理解错误
- 改颜色数应清掉旧结果，复制全部得到每行一个 HEX。代表色不保证存在于原图是明确的算法范围，不算缺陷
- 证据：`palette.ts:7-15,23-40`、`ImagePaletteTool.vue:11-20,32-37`

#### 3. 颜色格式转换

- `#33669980` 应产生大写 HEX8、`rgb(51 102 153 / 0.501961)`、`hsl(210 50% 40% / 0.501961)`；`#0000` 完全透明时通道仍保留
- `hsl(0.5turn 100% 50%)`、百分比 RGB 与逗号 RGBA 能进入同一闭环；超范围输入应拒绝，不能沿用上次结果
- 无 CMYK/Lab/颜色名是公开范围，不要求把基础转换器扩大为完整 CSS parser

- Windows 目标 WebView 中点击启动，选已知红/绿像素，返回对应大写六位 HEX并复制
- Esc、取消、30 秒超时后都应可重新开始；离页结果不回写；无 API 环境应显示不可用而非空转
- 不要求坐标记录、连续采样或截图
- 证据：`useScreenColorPicker.ts:6-35`

#### 5. 图片元数据清除

- 用含 GPS/相机/时间/Orientation=6 的 JPEG，处理后保留方向、删除私密标签，压缩扫描字节不变；在独立查看器确认方向一致
- PNG 文本/EXIF 移除，IDAT、透明块、必要色彩块保持。带 ICC 时清楚说明配置内部未清理
- 清除后的预览是元数据摘要，不是图像渲染；由于不重编码，文本摘要可以支撑基础功能，但不应宣称完全匿名
- APNG/MPO/不支持的 HDR 拒绝是合理范围；另验 EXIF 分辨率边界 IMG-07
- 证据：`imageMetadataStrip.ts:16-30`、`imageStripJpeg.ts:48-75`、`imageStripPng.ts:24-56`

#### 6. 图片元数据查看

- 有相机/拍摄时间/GPS南纬西经/Orientation=6 的 JPEG 能显示受支持字段，显示宽高交换正确；无 EXIF 的 PNG 仍显示格式、大小、位深和尺寸
- APNG 可报告帧数；XMP/IPTC/PNG文本/完整ICC不解析时明确标明范围，缺失字段不能解释为文件不存在该元数据

- 800×400 与 200×600 两图等比缩入 300×300，应为 300×150 与 100×300；不保持比例则都为 300×300

### 需要改进的问题

#### D-01 / P1：计算器自己的结果可能无法继续运算或复制

证据等级：确定算法错误；输入框、等号、继续运算和历史回填路径均存在，没有额外指数转换guard。

- 证据：`src/tools/components/CalculatorTool.vue:43–54` 词法只接受普通十进制，没有指数；`:122–125` 使用 `Number(...).toString()`，小数可变成 `1e-7`；`:127–136` 将结果覆盖回表达式；`:24–30,159–162` 复制依赖重新解析得到的实时结果
- 用例：输入 `1 / 10000000`，按等号；结果会写成 `1e-7`，实时解析失败，复制按钮消失。再点 `× 10 =` 报不支持 `e`，历史回填同样失败
- 改进：让结果表示与解析语法一致，或分离数值累算状态与展示字符串；不要以再次解析展示字符串作为复制前提
- 验收：极小/极大有效结果均可复制、历史回填、连续计算；`1/10000000 ×10` 得到可继续使用的 `0.000001` 或等价指数表示

#### D-02 / P1：单位换算把有效非零结果显示和复制成 0

证据等级：确定算法错误；数据容量B/GB/GiB均是现有选择项，复制直接取展示串。

- 证据：`UnitConverterTool.vue:57–66` 计算结果后固定 `maximumFractionDigits: 8`；`:83–86` 复制该格式化结果，无精度或近似提示
- 用例：数据大小 `1 B → GB`，真实值是 `0.000000001`，页面/复制为 `0`；`1 B → GiB` 也归零。极大有限输入乘比例还可能得到 `∞`，未做结果有限性检查
- 改进：按有效位或科学计数法展示，极小非零不能默认为精确 0；溢出明确报错；复制保留可计算精度
- 验收：1 B→GB、GiB 和极大数量均有正确结果/错误提示；显示与复制语义一致

#### D-03 / P1：截图标注会把编辑定位标记导出，文字草稿不随之输出

证据等级：源码可达UI流程；保存/复制只检查busy和sourceBitmap，不检查pendingTextPoint，已有“更换图片前确认”不保护此导出路径。

- 用例：打开图片，选择文字，点击画布并输入一段文字，不点“添加文字”，直接保存/复制。输出包含定位圆，却没有草稿文字

- 验收：输出无选中态/定位圆/拖动预览；文字待提交时不会悄悄丢失

#### S-01 / P1（破坏性操作静态风险）：临时清理检查对象与删除对象未绑定

证据等级：条件竞态/故障风险；已有token、默认不选、确认、路径/大小/mtime检查确实存在，本项只指出这些guard没有锁定同一文件对象，不声称普通点击必然误删。

#### S-02 / P1（目标安全）：结束端口进程只绑定PID，未绑定用户所确认的进程实例

证据等级：条件竞态风险；执行前会重新查询端口/PID并拒绝关键进程，已复核；缺的是原预览实例与最终操作对象之间的身份绑定。

- 改进：返回并确认稳定身份（至少PID+创建时间和可读映像信息），操作前核验并针对同一句柄执行；实例变更要求重查。不要为了功能强制提权/强杀
- 验收：隔离测试进程正常结束可核验；旧预览、退出/重启/身份变化应拒绝，不影响替代进程

#### S-03 / P1（导出安全）：区域截图直接截断已有输出，失败可能损坏原文件

- 改进/验收：统一为新文件另存，或明确支持安全替换；写入失败保留原文件字节和可重试截图；成功后回读确认可打开；目标冲突/取消/只读/磁盘错误都清晰提示

### 横向验收建议

1. 先以静态缺陷用例验证普通数值、结果失效、输入改变和导航；不需要先扩大支持范围
2. Windows中文与英文环境分别检查端口命令输出；125%/150%缩放和副屏验证截图/标尺/窗口移动，WebView2权限拒绝与取消必须恢复窗口
3. QR/条码下载、Tauri原生对话框另存、剪贴板文本/图片写回是真实闭环的最后一环；源码有调用不等于这些已通过
4. 系统写入、永久清理、进程结束、电源动作使用隔离测试对象和明确授权，报告必须记录未测试，不能拿构建成功替代
5. 不应把新增DNS服务器选项、完整Emoji集、历史云同步、系统PATH编辑、通用API集合管理作为所有模块“完成”的强制条件
